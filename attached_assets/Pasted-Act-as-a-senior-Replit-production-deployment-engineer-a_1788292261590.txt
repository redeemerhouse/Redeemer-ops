Act as a senior Replit production deployment engineer and fix the deployment/runtime failure preventing the Redeemer House application from launching.

This is a production deployment debugging task. Do not redesign the application, remove working features, replace the architecture, or make broad unrelated changes.

The current deployment logs repeatedly show:

* GET /api/healthz returning HTTP 503
* Replit reporting: `healthcheck failed error=healthcheck /api returned status 503`
* Repeated error: `Shared rate-limit store unavailable`
* The API server otherwise starts with:
  `node --enable-source-maps ./dist/index.mjs`
* Replit eventually sends SIGTERM because the deployment never becomes healthy
* PNPM then reports the start process was terminated

The SIGTERM appears to be a CONSEQUENCE of the failed health checks, not the original root cause.

Your job is to locate and fix the underlying production readiness failure.

PRIMARY SUSPECT:

The shared/distributed rate-limit store, or another dependency included in the `/api/healthz` readiness check, is unavailable in production and is causing the health endpoint to return 503.

However, do not assume this is the only problem. Verify it from the code.

PHASE 4 — RATE LIMITER FAIL-SAFE BEHAVIOR
=========================================

Review the rate-limiting implementation.

We need production-safe behavior.

DO NOT simply disable security protections.

Determine whether the application can safely use one of these approaches:

A. restore the intended shared rate-limit service

OR

B. gracefully fall back to an in-process limiter when the distributed store is temporarily unavailable

OR

C. fail closed only on sensitive endpoints while allowing the application health endpoint and public application shell to remain operational

Choose the safest approach for this architecture.

Important:

* Do not remove rate limiting.
* Do not expose authentication endpoints.
* Do not bypass authorization.
* Do not hard-code credentials.
* Do not commit secrets.
* Do not weaken CSRF/session/security protections.
* Do not use a permanent in-memory limiter for a horizontally scaled production architecture unless you clearly document the limitation.

If a Redis/Valkey/shared store is intended to be mandatory, fix the shared store rather than bypassing it.
